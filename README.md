        # sqlite — Лимиты и когда НЕ стоит

        Homework-шаблон для урока **l4_limits_and_when_not_to** (Лимиты и когда НЕ стоит) на платформе Vibe Learn.

        ## Что делать

        На Python (stdlib sqlite3) реализуй «советника по выбору СУБД» как чистую функцию плюс
демонстрацию лимита. Функция recommend(profile) принимает словарь признаков нагрузки
(concurrent_writers, multi_machine, need_roles, heavy_analytic_joins, read_heavy_single_server)
и возвращает 'postgresql' или 'sqlite' с обоснованием по дереву решений из урока. Плюс
напиши демонстрацию single-writer лимита: на :memory: (или файловой) базе запусти несколько
потоков-писателей без busy_timeout и зафиксируй рост ошибок «database is locked», показав
потолок конкурентной записи эмпирически. Тесты на :memory:: (1) recommend возвращает
'postgresql' для каждого «жёсткого» сигнала по отдельности и 'sqlite' для read-heavy single
server; (2) демонстрация single-writer воспроизводимо показывает блокировки при N писателях.

## Контекст (из transfer-задачи урока)

Стартап вырос. Сервис на SQLite (WAL, Litestream для бэкапа) последние полгода жил отлично:
read-heavy дашборд на одном сервере, ~30k чтений/сек, записей мало. Теперь продукт меняется:
(1) добавляют write-heavy фичу — поток событий от устройств, десятки тысяч вставок/сек с
множества клиентов; (2) команда хочет вынести аналитику в отдельный сервис на другой машине,
читающий те же данные; (3) безопасность требует, чтобы у разных команд были разные права на
разные таблицы; (4) появились тяжёлые аналитические отчёты с join-ами таблиц по 100M строк.

**Вопрос:** по каждому из четырёх изменений (1)-(4) скажи, упирается ли оно в реальный лимит
SQLite, в какой именно, и толкает ли это к PostgreSQL. Затем дай общий вердикт: остаться,
мигрировать целиком, или гибрид — и обоснуй. Не забудь про путь миграции/риски.

## Recap из урока

- Теоретические лимиты (база ~281 ТБ, строка ~1 ГБ, 2000 колонок) знать полезно, но они **почти никогда не определяют выбор**.
- Реальные границы: **один писатель** (потолок write-throughput), **одна машина / нет сети**, **нет шардинга**, **нет ролей**, **нет MVCC**. В один из них упирается почти каждое решение.
- **Оставайся на SQLite** для embedded / edge / mobile / тестов (`:memory:`) / read-heavy одного сервера (с WAL — вполне прод).
- **Переезжай на PostgreSQL** при много-писательской нагрузке, доступе с нескольких машин, шардинге, ролевой безопасности, тяжёлой аналитике (там hash/merge join vs nested-loop у SQLite).
- Итог курса: SQLite — **не «маленький PostgreSQL», а другой класс инструмента**; выбор — про модель доступа (локальный single-writer vs сетевой multi-writer), а не про «серьёзность» базы.

        ## Локальное окружение

        - Python 3.12+
        - SQLite встроена — **никакого сервера и docker-compose**. БД это один файл (`DATABASE_PATH`) или `:memory:` в тестах. Модуль `sqlite3` входит в stdlib, ставить драйвер не нужно — единственная зависимость это `pytest`.

        ## Запуск

        ```bash
        # Установить зависимости (только pytest)
        pip install -r requirements.txt

        # Прогнать тесты (бегут на :memory:-базе, ничего поднимать не нужно)
        pytest

        # Запустить main (печатает marker; замени stub на реализацию)
        python main.py

        # На файловой БД (нужно для backup/vacuum-уроков):
        DATABASE_PATH=./app.db python main.py
        ```
